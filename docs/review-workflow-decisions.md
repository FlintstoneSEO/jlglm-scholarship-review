# Review Workflow Decision Register

Date: 2026-09-26. Source: [application redesign audit](application-redesign-audit.md), findings A1–A7. This register records choices required before changing submission, authorization, scoring or persisted data. **Every decision below is OPEN.** Recommendations describe options for discussion, not approval or a new rule. Preserve current behavior until a decision is made and tested against production-like data and RLS.

| ID and decision | Why it matters; current behavior | Options to decide | Implementation impact and validation | Decision |
|---|---|---|---|---|
| **D1. Submitted review editing** — May a reviewer change a final submission? | Both UIs and owner update policies currently allow changes after completion; Scholarship Save draft preserves `is_complete=true`. A final label could mislead reviewers and admins. | **A** immutable after submission; **B** reviewer can reopen until deadline; **C** administrator can reopen; **D** always editable. Specify whether scores, comments, timestamps, and history all follow the same rule. No option is selected. | Define state transitions and permissions for both UI and MCP, preserve history/version or create an audit trail if required, then test direct RLS/API access, concurrent edits and already-completed aggregates. Blocks Phase D. | **OPEN — project direction required.** |
| **D2. Scholarship duplicate review identity** — What enforces one reviewer/one application? | Legacy `reviews` has no verified unique `(applicant_id, reviewer_id)` constraint; UI and MCP read then insert. Duplicates can increase the fixed five-review count and total. | Establish one canonical review row per applicant/reviewer; decide how pre-existing duplicates are reconciled (retain with audit history, select canonical by explicit rule, or adjudicate case by case) and whether a uniqueness constraint plus idempotent write is required. Do not guess a survivor. | Read-only inventory of duplicate pairs, score/status impact and writer paths; approved reconciliation and reversible migration; concurrent UI/MCP test. Blocks any write unification. | **OPEN — identity and duplicate-resolution rule required.** |
| **D3. Eligibility revocation** — What happens when an assigned Scholarship applicant becomes ineligible? | Eligibility creates assignments; reverting screening does not remove them. Queue UI hides ineligible records, while assignment-based RLS may still allow direct reads. Existing reviews/documents may remain. | Decide reviewer access after revocation; visibility of completed reviews; archive, suspend or remove assignments; whether re-eligibility restores access. Explicitly decide retention for review, notes, discussion files and audit history. | Requires RLS/storage policy and assignment lifecycle design, not just UI filtering. Test applicant/header/review/note/document reads with assigned reviewer tokens before and after each screening transition. Blocks Phase B access claims and Phase D. | **OPEN — committee/security direction required.** |
| **D4. Grant submission atomicity** — Which writes form one commit? | Grant save currently creates `program_reviews`, upserts `review_scores`, then updates status/comments/timestamps. Network interruption can leave a partial draft. | Preferred proposal for decision: review identity, all criterion scores, reviewer comments and final submission status/timestamp commit together in one authorized transaction. Decide whether draft saves use the same boundary, retry idempotency key, stale-version behavior and recovery of existing partial rows. | Design an authorized server/DB boundary consistent with RLS; verify failed stage rollback, retries, score totals, `portal_applications` aggregates and admin views. No transaction API is chosen here. Blocks Phase D. | **OPEN — transaction and retry semantics required.** |
| **D5. Scholarship reviewer count** — Is five permanent? | Legacy completion trigger marks reviewed at five complete rows and UI labels combined score out of 90. Current assignments may differ from five. | Keep exactly five as the continuing rule, or plan a separately specified configurable reviewer count and score denominator. Preserve five until explicitly changed. | Any configurable version needs business rule, migration for historical meaning, aggregate/report updates and regression tests. Read-only Phase A must flag assignment-count discrepancies without changing completion. | **OPEN — confirm fixed or future configurable.** |
| **D6. Business Growth Grant rubric** — What are the approved criteria? | `rubric_criteria` is dynamic; migration intentionally seeds no guessed grant rubric. | Committee supplies criterion names, descriptions, maxima, order, active dates/version policy, and how existing scored reviews behave if criteria change. | Validate configured rows against approval before production scoring; test per-review totals, completed averages and ranking after rubric changes. No guessed criteria or maxima. | **OPEN — approved rubric required.** |
| **D7. Global admin program selection** — How does a newly promoted global admin enter each program? | SQL global-admin helper grants broad access, but the selector is built from membership rows; changing global role does not add memberships (A4). | Give global admins all programs in the selector without membership rows, provision explicit memberships on promotion, or require deliberate per-program grants. Decide how program admin differs from global admin in Scholarship editing. | Align selector, effective capabilities and RLS; test new admin, removed membership, direct URL and cross-program roles. This is a UX/access decision, not permission to widen RLS. Blocks Phase B. | **OPEN — access administration direction required.** |
| **D8. Peer review visibility and comparison** — Who may see individual peer scores and when? | Current RLS restricts reviewers to own rows; Scholarship admin comparison and grant admin views need broader scope. Aggregate progress may be visible without peer identity. | Confirm whether admins only see named peer scores, whether reviewers ever see anonymized/aggregate results, and any timing rule after submission. | Keep current RLS until approved. Test routes and direct queries with admin, reviewer, viewer and cross-program accounts; separate count visibility from row visibility. | **OPEN — confirm comparison policy.** |
| **D9. Navigation and screen specification** — Which changes to task hierarchy are approved? | Existing routes can support shared reviewer flow; mobile shell omits some shared admin links (A7). Scholarship-only Notes/Contact and grant-only Rubric/Rankings differ legitimately. | Confirm proposed reviewer/admin IA in the [plan](review-workflow-unification-plan.md), including mobile admin entry, section order, queue return behavior and program-specific destinations. | Required before a shared workspace or visual implementation; route preservation is recommended. Test every authorized task at required widths. | **OPEN — IA approval required before Phases C/E.** |

## Decision recording and gate

For each row, replace **OPEN** only with the selected rule, decision maker/date, affected programs, transition/retention behavior, and links to test evidence or an approved migration plan. Record consequential choices in `templates/design-decision-log.md` during implementation planning. D1–D6 and D7 affect correctness or access; do not infer an answer from today's permissive UI/policies. Read-only adapter work can proceed while these remain open, provided it reports anomalies and leaves native writes and RLS untouched.
