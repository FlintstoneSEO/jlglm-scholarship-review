# Login reliability and release identification

Authorized by the October 13 request: add login version identification, fix refresh returning signed-in users to login, and offer saved username/email. This is a bounded usability/authentication repair, not Phase F release authorization.

## Audit and preservation

- **Severity:** high. **Element:** `src/routes/_app.tsx`. **State:** hard refresh or direct protected URL. **Observed problem:** `beforeLoad` checks the browser-persisted Supabase session during SSR, where browser storage is unavailable. **Evidence:** the guard calls `getSession`; `client.ts` persists through `brokeredPreviewStorage`, which returns no storage on the server. **Exact change:** use TanStack Start selective `ssr: false` on the protected layout and login route so existing guards run during browser hydration. Children inherit the layout's restriction. **Reason:** session checks must run where the existing session is stored. **Expected outcome:** refresh retains the requested URL and session; missing sessions still redirect. **Verification:** synthetic browser hard-refresh/direct-entry tests, signed-out redirect and setup gate tests.
- **Severity:** low. **Element:** login form. **State:** returning signed-out user. **Observed problem:** no explicit email preference and password lacks autocomplete metadata. **Evidence:** email/password states initialize empty, no remember control, email uses `autocomplete=email`. **Exact change:** optional unchecked remember-email checkbox with local-only email storage after successful login, immediate removal on uncheck, safe unavailable-storage handling, `username` and `current-password` autocomplete plus field names. **Reason:** reduce repeated entry while preserving user control. **Expected outcome:** opted-in email prefilled after sign-out/revisit; no app-managed password storage. **Verification:** opt-in, opt-out, failed-login and storage-failure fixtures.
- **Severity:** low. **Element:** login screen. **State:** support/version checking. **Observed problem:** no release identifier. **Evidence:** no package version or rendered release label. **Exact change:** establish package version 1.0.0 and compile version plus UTC build timestamp into the UI. **Reason:** identify the actual bundle loaded, including successive builds of the same release. **Expected outcome:** readable bottom-left label across supported widths. **Verification:** build output and rendered responsive checks.

No schema migration, cookie migration, role/RLS change, session lifetime change, new account, real review mutation or hosted configuration change. Server functions still validate bearer claims; database/storage RLS remains authoritative. Browser session data remains an input to UI guards, never a new server authorization source. Preserve safe return paths, invitation/setup completion, recovery handling and existing sign-out semantics. No server-side private data is rendered by the protected layout.

## Screen specification and decisions

Preserve the existing Phase E split login composition, brand panel, typography and tokens. Primary action remains Sign In; secondary action remains Forgot password. Place the native checkbox and its wrapping label below password, with a 44 CSS-pixel minimum label target and visible focus. Include device-local privacy helper text and a persistent message if saving the preference fails. Keep password manager support native.

Desktop version metadata sits below the copyright in the left brand panel. Compact layouts display the same label at the bottom left in document flow below the form, never over controls or the keyboard. Use existing white-on-sidebar and muted-foreground-on-background colors. The version identifies the loaded release; it does not claim to have checked the latest deployed release. Future releases bump `package.json` version; every production build gets a fresh UTC build identifier automatically.

No navigation/IA or visual-direction change. No new generic primitives are warranted for these two small additions. Browser/client-only rendering is limited to the existing browser-authenticated route subtree and login route; public reset/invitation flows retain their current behavior.
