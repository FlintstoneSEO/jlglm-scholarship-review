# Review Workflow Unification Plan

Date: 2026-09-26. Planning baseline: commit `06bbd1ef3001c19ce60171fef45a09af68c88e22` and [application redesign audit](application-redesign-audit.md). This is a proposed application contract, not an implementation or a finding about the deployed database. The earlier [architecture audit](architecture-audit.md) describes a pre-migration baseline; current migrations and routes take precedence. No code, route, style, schema, policy, or record changes are authorized by this plan.

## Target and preservation boundary

One portal presents one reviewer task sequence and one rubric/review presentation engine through program adapters. React/TanStack Start file routes, Cloudflare deployment, Supabase Auth/RLS, the program selector, and both persistence models remain. Shared mechanics may own queue navigation, status labels, progress layout, failure states, document presentation, score input layout, and draft/submit affordances. Adapters own source queries, rubric definitions, score arithmetic, completion rules, document provenance, and eventual writes. A shared presentation engine must take explicit criterion descriptors and score units; it cannot treat Scholarship's fixed combined score as a grant average.

The audit's **Preserve** items are legacy Scholarship applicants/reviews, screening, five-reviewer sum and selection; grant dynamic criteria, typed content, criterion scores and average ranking; and native architecture and authorization. **Improve** error/unsaved feedback, metric labels, and mobile admin access. **Restructure** read-only queue, workspace, progress and capability presentation. There is no recommendation to replace either persistence model. This plan keeps findings A1–A7 and their evidence in the audit as open work, including the A1 monitoring mismatch, A2 duplicate/revision risk, A3 multi-write grant submit, A4 role mismatch, A5 screening/access mismatch, A6 stale/error states, and A7 navigation/score vocabulary.

## Contract conventions

These are proposed TypeScript-facing shapes, not database types. Every read result carries `programId`, `applicationId`, source provenance, `loadedAt`, and an explicit `loading | ready | empty | partial_error | error | unavailable` result state. `unavailable` must not reveal whether a forbidden record exists. A secondary-query failure is `partial_error`, never an empty list. Adapter calculations use source rows the caller is authorized to read; an admin monitor may receive broader data than a reviewer. Views and controls use effective capabilities for presentation, while Supabase grants, RLS, and storage/provider permissions remain authoritative. No browser-side capability calculation confers access.

| Contract | Responsibility and proposed inputs | Outputs and state | Ownership: shared / program-specific |
|---|---|---|---|
| `ReviewQueue` | Find assigned or otherwise authorized work. Input: actor, selected program, filters/search/sort, page, queue scope. | Rows with application identity, assignment, `ReviewStatus`, `ReviewProgress`, destination and return context; loading/empty/error/unavailable and filter state. | Shared filtering controls, table semantics, return behavior; adapter owns authorized query, fields, screening and program filters. |
| `ReviewWorkspace` | Organize overview, application, documents, rubric, comments, actions. Input: queue row/application ID, actor, adapter data, capabilities, return target. | Sections, active section, dirty/saving/saved/error/conflict/submitted presentation state and action descriptors. | Shared shell, focus/keyboard behavior, unsaved guard, action placement; adapter owns narrative, Scholarship notes/contact/discussion, criterion model and data requests. |
| `ReviewProgress` | State how much review work exists and is complete. Input: assignments, own review, visible review summaries, program completion rule. | `assignedReviewers`, `startedReviews`, `completedReviews`, `remainingReviews`, denominator kind/value, anomalies and source timestamp. State: pending/known/partial/error. | Shared labeled display; adapter owns counting, deduplication policy and completion rule. Do not silently hide legacy duplicates. |
| `ReviewPermissions` / `EffectiveCapabilities` | Determine which tasks to offer. Input: global role, program role, selected program, assignment, application state, screening/eligibility, submission state, source loading state. | Boolean capabilities with reason/unknown per action; unavailable/unknown while authorization inputs are unresolved. | Shared presentation contract; adapter supplies program constraints. RLS is the final authority. |
| `ReviewSubmission` | Describe draft/submit validation and future write boundary. Input: actor, assignment, record/version, criterion values, comments, intent (`save_draft` or `submit`), idempotency key when supported. | Proposed result: saved snapshot/version, status, timestamp or typed validation/conflict/authorization/partial-write error; idle/dirty/validating/saving/saved/submitting/submitted/conflict/error state. | Shared UX state and error vocabulary; each adapter owns validation and persistence. No common write service or transactional claim exists yet. |
| `ReviewStatus` | Normalize per-review task state separately from application aggregate state. Input: assignment, native review status, application status, screening, availability. | `unassigned | assigned | not_started | in_progress | submitted | reopened | unavailable`, plus native value and reason; unknown when required reads fail. | Shared labels/badges; adapter owns mapping. `reopened` is reserved pending a revision decision. |
| `ReviewScoreDisplay` | Present rubric and totals with unambiguous units. Input: criterion descriptors, permitted score values, native totals, completion rule, audience. | Criterion rows, reviewer subtotal, application aggregate, max/denominator, aggregation label, pending/partial/ready state. | Shared accessible score/rubric rendering; Scholarship owns Writing/Rhetoric 0–9 and completed-only sum /90; grant owns configured criteria, review sum and completed-review average. |
| `SupportingDocuments` | List and open authorized attachments with provenance. Input: application, actor, adapter document descriptors. | Label, kind, source (`external | private_storage | scholarship_original | discussion_copy`), access/open action, missing/loading/error/denied state. | Shared list/viewer affordances; adapter owns types, provider URLs, signed URL retrieval and access boundary. External provider access is separate from RLS. |
| `ReviewerComments` | Present and edit the reviewer's review comments, with read visibility and draft state. Input: own review, actor capabilities, adapter field mapping. | Text, dirty/saved/conflict/error state and permitted actions. | Shared form feedback/accessible labels; Scholarship maps reviewer notes and retains separate applicant notes/contact logs; grant maps `program_reviews.reviewer_comments`. |
| `ReviewNavigation` | Keep reviewer orientation and return path; expose admin tasks. Input: program, actor/capabilities, queue context, application ID, section. | Task destinations, breadcrumb/previous-next/return descriptors, current task and mobile disclosure state. | Shared navigation model and accessible behavior; adapters map existing routes and program-only destinations. |

Do not derive `ReviewProgress` from only `portal_applications.completed_review_count` for Scholarship. Do not turn a failed review query into zero progress. A reviewer-visible progress display may show only aggregate counts, while admin comparison can show permitted peer detail; capability and query scope must agree.

## Program adapters

`ScholarshipReviewAdapter` reads `portal_applications` for shared identity/assignment context and legacy `applicants`/`reviews` for application, screening, score and completion truth. It exposes fixed Writing and Rhetoric criterion descriptors (0–9 each), own legacy review, completed legacy review count, completed-only combined sum out of 90, and a fixed five-reviewer completion target. It preserves historical applicants/reviews, preliminary screening, automatic assignment behavior, finalist/selected flags, original essay/transcript links, reviewer discussion copies, applicant notes and contact logs. The current UI and MCP `submit_review` are separate writers; both remain untouched until the identity/revision decision and duplicate inventory. For A1, its read-only admin progress projection joins assigned application/reviewer identities to legacy reviews, reports unmatched/duplicate rows as anomalies, and reconciles with the applicant and portal status rather than inventing `program_reviews` rows.

`BusinessGrantReviewAdapter` reads `portal_applications`, `business_grant_application_details`, `reviewer_assignments`, `rubric_criteria`, `program_reviews`, `review_scores`, and `application_documents`. It exposes live active criterion descriptors and maxima, own criterion points/comments, per-review total, completed-review application average, and assignment-relative completion. It preserves raw form response, typed details, import identity, grant document categories, rankings and private/external document distinctions. Its current save path has separate review insert, score upsert and status/comment update operations (A3); the future write interface is only a proposal until atomicity, revision, retry and authorization decisions are validated. No Scholarship screening rule or fixed five-reviewer denominator is applied to grants. Approved grant rubric criteria must be confirmed before production scoring configuration.

Adapters should implement the same read-facing interface (`loadQueue`, `loadWorkspace`, `loadProgress`, `mapStatus`, `getScoreDisplay`, `listDocuments`, `getNavigation`, `deriveCapabilities`) with program-specific implementations. A later `saveDraft`/`submitReview` interface is gated in Phase D. Normalize identifiers to `programId`, `applicationId`, `assignmentId?`, and `reviewId?`; retain native IDs for writes, never infer one table's ID from another. Keep source timestamps and errors so the workspace can identify stale data.

## Normalized states and progress

| UI state | Scholarship mapping today | Grant mapping today |
|---|---|---|
| `unassigned` | No assignment for this reviewer; do not offer review. | No `reviewer_assignments` row. |
| `assigned` / `not_started` | Assigned eligible applicant with no own legacy review; use `not_started` for task status. | Assignment exists with no review or native `not_started`. |
| `in_progress` | Own `reviews` row with `is_complete=false`; applicant aggregate may also be `in_progress`. | Own `program_reviews.status=in_progress`. |
| `submitted` | Own `reviews.is_complete=true`; applicant `reviewed` means five completed legacy reviews, not merely this submission. | Own `program_reviews.status=completed`; portal `completed` is an application aggregate computed against assignments. |
| `reopened` | No distinct persisted state. Pending decision; do not infer it from a post-submit edit. | No distinct persisted state. Pending decision. |
| `unavailable` | Missing/denied record, failed screening access, or denied assignment, with reason exposed only when safe. | Missing/denied record, absent assignment, or denied program access. |

`assignedReviewers` is distinct assigned reviewer identities; `startedReviews` is assigned identities with draft or submitted records; `completedReviews` is assigned identities with submitted records; `remainingReviews` is denominator minus completed (clamped for display, with overage flagged). Scholarship also reports the raw completed legacy row count because its trigger currently counts rows, and a duplicate can affect the fixed-five status/score. Its denominator is **5**, with an assignment-count discrepancy flagged. Grant denominator is current assignment count; an empty assignment set is **0 assigned**, not “fully reviewed.” Grant completed count and average come from `program_reviews` trigger output and must be reconciled against assignment-linked reviews. Do not equate `reviewed` with `completed` without the adapter's aggregate context.

## Effective capabilities

The proposed output includes `canViewApplication`, `canReviewApplication`, `canSaveDraft`, `canSubmitReview`, `canEditSubmittedReview`, `canViewPeerReviews`, `canManageAssignments`, `canConfigureRubric`, and `canViewRankings`. Each is `allowed | denied | unknown` with a reason and source; unknown disables actions and asks for a retry. Determine global role and program role first, then selected program, assignment, native application state, Scholarship screening, review state and query availability. Global admin overrides in SQL need their own tested selector/navigation rule (A4); program admin does not automatically gain Scholarship global-admin edit powers. Reviewer write affordances require an own assignment and program authorization. Scholarship screening currently limits queue UI but may not revoke direct RLS access (A5), so `canReviewApplication` must not claim an enforced revocation until the policy decision is implemented and tested. `canEditSubmittedReview` is decision-pending even though current policies permit owner updates. Peer-review viewing is admin-only where RLS permits it; never infer permission from a visible count. Grant rubric management/rankings are program-admin tasks; Scholarship selection and scoring summary remain separate administrative tasks. Explicitly test global admin, program admin, reviewer, viewer, no access, global-viewer/program-reviewer and cross-program combinations against deployed RLS before relying on this model.

## Target information architecture

Reviewer mental model: **My Reviews → program Review Queue → Application workspace → Overview / Application / Documents / Rubric / Comments → Save Draft or Submit Review → Return to Queue**. Scholarship-only Notes, Contact and discussion documents remain accessible as program sections; they are not merged into review comments. Workspaces show own status and score units. Previous/next obey the authorized, filtered queue. Unsaved navigation must offer a recovery choice in a later UI phase.

Admin mental model: **Program dashboard → Applications / Reviewer Assignments / Review Progress → application comparison → program report or selection**; **Users & Access** and **Rubric** appear only for authorized roles/programs. Scholarship Scoring Summary and finalist/selected controls remain Scholarship-specific; Grant Rankings and rubric configuration remain grant-specific. Mobile navigation must reach the same authorized shared admin tasks as desktop. Existing `/applicants`, `/applicants/$id`, `/grants`, `/grants/$id`, `/assignments`, `/users`, `/top`, `/grant-rankings`, and `/grant-rubric` routes can be preserved while shared read components and labels are introduced. Any later route consolidation is a separate IA decision, not a prerequisite.

## Immediate handoff

- **Safe now:** Read-only baseline inventory, fixture design, isolated adapter contracts/projections and labels that do not alter writes or claim new access.
- **Business decisions:** Submitted-review editing/reopening, one Scholarship review identity, eligibility revocation and history, grant transaction/retry boundary, fixed versus configurable Scholarship reviewer count, approved grant rubric, and global-admin program selection (see [decision register](review-workflow-decisions.md)).
- **Database validation:** Applied migrations/RLS, role-scoped reads and writes, duplicate legacy reviews, assignment/review reconciliation, screening changes, grant partial writes and aggregate triggers, storage/provider access.
- **Program-specific:** Application content, screening/selection, rubric criteria and maxima, score math/denominator, persistence, document categories/source and Scholarship notes/contact/discussion.
- **Shared:** Queue/workspace shell, normalized states, explicit progress and score presentation, capability-driven affordances, navigation, loading/error/unsaved feedback and accessibility behavior.
- **Recommended first implementation phase:** Phase A, after read-only baseline inventory and with native read paths retained for comparison. No write or UI redesign is part of Phase A.
